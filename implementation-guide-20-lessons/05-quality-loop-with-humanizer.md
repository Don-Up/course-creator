# 阶段 05：让质量成为有证据的有限闭环

**预计投入：** 8 至 12 小时。

**一句话目标：** 用 Gate、Finding、RepairTask、Candidate 与独立 Verification 取代 V0 那句"模型说通过"，让每一个质量结论都可以追溯到具体的检查、具体的证据和具体的人。

**这不是终态：** 质量闭环已经可控，但执行进程崩溃时仍然没有 Worker 接管能力。那是阶段 06 要解决的问题。

## 你将完成什么

V0 的质量节点可能只有一句摘要——"质量检查通过"——你不知道它检查了什么、怎么检查的、谁做的判断。修复可能直接覆盖原正文，作者可能自己宣布修复成功，循环可能永远继续，因为没有人说"停"。

这个阶段要解决的就是这个问题。完成之后，每个候选课程都会先经过确定性检查——标题全不全、字段对不对、链接能不能用——不需要模型判断的规则先跑。然后经过教学或语义量规检查，确认学习目标是否被满足。再经过 `humanizer-zh` 的语言质量 Gate，检查中文表达是否自然。每一步的检查结果都写成 `Finding`，指向具体的 Artifact 和位置。`RepairTask` 只读取必要的上下文，修复写成 `Candidate Artifact` 新版本，原版本保留不动。`Verification` 独立于作者判断——不是你修了你说过了就算，而是验证者重新跑一遍 Gate。通过之后才替换可用版本。失败有次数预算，也有成本预算，超过预算升级人工。Humanizer 在整个流程中只能做表达判断，不能替代事实、教学、构建或 release 判断。这会是你第一次拥有"可审计的质量"——你不再需要相信任何人的口头保证。

## 你现在站在哪里

阶段 04 已经把 quality 做成了图中的一个节点，但节点内部可能只有一句摘要。本阶段将这句摘要拆成对象、Gate、候选版本、独立验证和退出条件——让质量从"一个感觉"变成"一组可追溯的事实"。

## 两份 Skill 在本阶段的角色

`teach-generator` 定义了多层质量理念：它要求确定性检查、要求量规审查、要求 Humanizer 与人工审核共同工作。本阶段把这些理念从 Skill 文本翻译成可执行的 Gate 和 Finding。`humanizer-zh` 专注中文表达的机械痕迹、语气和可读性——它产生表达类 Finding，但不判定资料是否真实、不判定教学目标是否达成、不判定 Markdown 构建是否成功、不决定发布。这个边界在 V0 阶段就被画好了，但本阶段是第一次用代码把它真正执行出来。

## 质量链

```text
Lesson Candidate
  -> deterministic gate
  -> rubric gate
  -> humanizer-zh gate
  -> Finding[]
  -> RepairTask(minimal context)
  -> Candidate v2
  -> independent verification
  -> accepted artifact | human escalation
```

这条链里有几个关键设计：Finding 是事实——不是"感觉不太好"，而是"第 3 节缺少必须标题 H2"。RepairTask 是待办——不是"重写整章"，而是"修复第 3 节的标题"。Candidate 是新版本，原版本不能被静默覆盖。Verification 是独立判断，不是作者说"我修好了"就算。每一步都可以被审计，每一步都有明确的负责人。

## 分步任务

本阶段的任务顺序反映了质量闭环的自然工作流：先定义 Gate 和 Finding 的结构，因为后面的所有步骤都依赖它们；然后按成本从低到高实现 Gate——确定性检查成本最低先做，量规次之，Humanizer 主观性最强最后做；最后实现修复和验证，因为它们依赖 Gate 的输出来驱动。这个顺序让你在每一步都能独立验证，而不是等到最后才发现问题。

### 任务 1：定义 Gate 与 Finding

Gate 写清输入、输出和失败类型。Finding 写严重度、类别、证据位置和建议，关联到具体的 Artifact 版本。不要只保存自然语言总结——"质量有问题"不是 Finding，"第 3 节缺少 H2 标题"才是。完成定义是前端能定位到具体问题。证据是 Gate 与 Finding 的测试，用固定 Markdown 夹具验证每种 Gate 能产生正确的 Finding。

### 任务 2：先做确定性检查

检查必需标题是否存在，检查必要章节字段是否完整，检查链接或渲染基本约束是否满足。这些检查不依赖模型判断——它们是可以写成代码的规则，失败直接写 Finding，不需要"模型觉得"。证据是固定 Markdown 夹具，确认缺少标题的文档能被正确识别。

### 任务 3：接入量规与 Humanizer

量规检查任务是否符合学习目标——教学目标有没有被覆盖、前置知识是否被补齐。Humanizer 检查中文表达——有没有宣传腔、翻译腔、AI 高频词汇。两者输出不同类别的 Finding，不要合并为一个分数。不要在 Humanizer 中编造事实建议——Humanizer 只能说"这段文字读起来像机器翻译"，不能说"这段内容的事实有误"。证据是分类夹具，确认同一段文本的量规 Finding 和 Humanizer Finding 是分开的。

### 任务 4：实现 RepairTask 与 Candidate

RepairTask 只带问题片段、相关规则和目标——不是整章正文，不是整份 Skill。修复角色不能获得整个隐私来源包。修复写成 Candidate 新版本，原版本仍然可读取。完成定义是修复可审计——你可以在事后看到"谁因为什么 Finding 修改了什么"。证据是版本关联测试。

### 任务 5：独立 Verification

验证者不重复作者"已修好"的话——它重新运行对应 Gate，只有通过才标记 Candidate 可用。如果失败，重新产生 Finding 或升级人工。证据是作者错误自评夹具——模拟一个修复声称"已修好"但实际仍有问题的场景，确认 Verification 能识破。

### 任务 6：设置双预算

限制每个 Finding 的修复次数——同一个问题不能被无限次修复，因为如果三次修复都没解决，第四次大概率也解决不了，它需要人工判断。限制每个 Run 的总修复成本或次数——因为一个 Run 可能有多个 Finding，每个单独看都在预算内，但加起来会让整个 Run 永远无法完成。每次循环记录预算消耗，超过上限必须停止自动修复。完成定义是人工出口可见且可触发。证据是上限测试，确认达到上限后循环真的停止了。

## 关于质量闭环的补充说明

质量闭环是本项目中最容易被"过度简化"也最容易被"过度设计"的模块。过度简化是指：三个 Gate 合并成一个，Finding 用自然语言描述，Repair 直接覆盖原文，Verification 被省略。过度设计是指：为每一种可能的错误类型建一张表，定义了十几个 Gate 但大部分用不上，预算系统复杂到需要专门的配置界面。本阶段的目标是在两者之间找到平衡。

**Gate 的顺序为什么重要。** 确定性检查必须先跑，因为它是唯一不需要模型调用的检查，成本最低。如果标题缺失，你不需要让模型来判断"这个课程质量如何"——标题缺失是事实，不是判断。量规检查在第二步，因为它需要模型参与但成本可控。Humanizer 在最后，因为它的判断最主观、最容易被误用。如果 Humanizer 先跑，它可能会对还没通过结构检查的文本产生大量无意义的 Finding。这个顺序不只是为了优化成本——它是为了让每一种 Finding 都有明确的上下文。

**Finding 的粒度。** Finding 应该指向具体的、可操作的问题。好的 Finding："第 3 节缺少 H2 标题"、"第 2 段的代码示例缺少语言标注"、"第 5 节的练习没有提供参考答案"。坏的 Finding："整体质量有待提升"、"部分内容不够深入"、"建议增加更多示例"。坏的 Finding 无法转化为 RepairTask——Repair 角色不知道"有待提升"是什么意思，它需要知道具体应该修改什么。

**双预算的设计。** 每个 Finding 的修复次数限制防止同一个问题被反复修复，每个 Run 的总修复成本限制防止整个 Run 陷入无限返工。两者缺一不可。只设总预算，一个顽固的 Finding 可能消耗全部预算；只设单 Finding 预算，多个小问题累积起来可能让 Run 永远无法完成。预算耗尽后的人工升级不是"系统失败了"——它是"系统在可接受的范围内自动处理了能处理的问题，剩下的需要人来做判断"。

### 关于测试策略的说明

本阶段的测试需要特别关注"边界条件"。Gate 顺序测试：确认确定性 Gate 在量规和 Humanizer 之前运行，确认 Humanizer 不会先于结构检查产生 Finding。版本保留测试：确认修复后原版本仍然可读，确认 Candidate 被接受后原版本没有被删除。预算测试：确认单 Finding 预算耗尽后该 Finding 不再被自动修复，确认总预算耗尽后整个质量循环停止。独立验证测试：构造一个"作者声称已修复但实际仍有问题"的场景，确认 Verification 能识破——这是最容易出错的测试，因为你需要让 Fake Provider 在修复时返回"看起来对但实际不对"的输出。

## AI 交付后的人类 Review
AI 交付代码之后，你重点检查三件事。第一，Humanizer 的 Finding 是否只包含表达类问题——如果有 Finding 说"缺少对 XXX 概念的介绍"，那 Humanizer 越界了。第二，修复后的 Candidate 是否保留了原版本——如果原版本被删除了，你失去了质量审计的能力。第三，预算耗尽后系统是否真的停止了——不要只看日志，亲自触发一次预算耗尽，确认循环不再继续。


检查每个"通过"结论是否有对应的 Gate 证据——不是"检查通过"，而是"确定性 Gate 通过，检查了 3 个规则"。检查 Finding 是否指向具体版本和位置。检查 Humanizer Finding 是否只是表达问题——如果它说"事实有误"，那就是越权了。检查修复是否写成了新 Candidate 而不是覆盖原版本。检查验证者是否重新跑了 Gate 而不是相信作者的话。检查次数和成本是否都有限制。检查人工升级是否真的能中断自动循环。检查技术方案是否描述了提交规则。

## 常见跑偏方式

用一个模型分数代表所有质量维度，让 Writer 自己决定自己是否通过，将 Humanizer 用来补来源事实，修复直接覆盖已接受版本，不保存 Finding 只保存最后文本，只限制循环次数不限制成本，预算耗尽后继续静默重试。这些做法都会让质量失去可信证据——你会以为自己有质量闭环，实际上和 V0 那句"模型说通过"没有本质区别。

这些跑偏方式背后有一个共同的根源：把"质量"当成一个可以通过一个分数或一句"通过"来概括的东西。质量不是结果，质量是过程——是你能追溯到每一步谁检查了什么、发现了什么问题、谁修复的、谁验证的。如果你把三个 Gate 合并成一个，把 Finding 写成自然语言，把 Verification 省略掉，那你和 V0 那句"模型说通过"没有本质区别——你只是写了一个更长的质量节点，但它产生的结论同样不可信。

## 完成后的系统快照

质量已有分层事实——确定性、语义、表达三个层次各自独立，各产生不同类别的 Finding。修复已有明确范围——RepairTask 只带问题片段和相关规则，不是整章重写。新旧版本可比较——Candidate 和原版本共存，你可以看到修复改变了什么。自动返工有边界——次数和成本两种预算，耗尽即停。人工可在质量风险处接管——不是系统失败，是系统在可接受范围内完成了能做的，剩下的需要人判断。长任务仍未从 API 进程中分离——那是阶段 06 要解决的核心问题。
