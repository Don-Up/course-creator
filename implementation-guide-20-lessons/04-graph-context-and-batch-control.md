# 阶段 04：用 Graph 管住顺序、上下文与批次

**预计投入：** 8 至 12 小时。

**一句话目标：** 用 LangGraph 的 State、Node、Edge 和条件路由替换 V0 的函数串联，让七步的执行顺序、审批门禁、上下文裁剪和批次控制都变成可审查的显式结构。

**这不是终态：** 图能控制流程了，但长任务仍然由当前进程运行，崩溃后无法安全恢复。那是阶段 06 要解决的问题。

## 你将完成什么

阶段 03 已经把角色拆开了，但 V0 的执行顺序很可能还是 `mission(); blueprint(); writer()` 这样的函数串联。顺序藏在函数内部，审批只能靠临时 `if`，批次只能靠循环变量，上下文越传越大，失败之后不知道应该回到哪一步。你没办法从代码里直接读出"这个系统在什么情况下会走到哪一步"——你只能跑一遍然后观察。

这个阶段要解决的就是这个问题。完成之后，七步仍然是用户可见的流程，但每一步都变成了图中的显式节点：每个节点有明确的输入和输出，每条边有明确的条件——成功走哪条边、失败走哪条边、等待人工走哪条边、未知状态走哪条边。release 是图中的人工门禁，不是自动流转。generation 可以按批次推进，每批只读取自己需要的 Context Pack，连续性台账保留前一批的关键事实。循环有次数和成本的上限，达到上限后升级人工而不是静默继续。图的状态不保存正文全文——正文仍然在 Artifact 里，Graph State 只保存引用。这会是你第一次能真正"看懂"这个系统的控制流，而不是靠猜。

## 你现在站在哪里

阶段 03 已经拆出了角色和 Artifact，但执行顺序仍然藏在函数调用里。本阶段用显式图替换这些隐式控制流——不是把函数调用换成图调用，而是让控制流本身变成可审查的一等公民。

## 两份 Skill 在本阶段的角色

`teach-generator` 规定了先任务定义、再蓝图、再批量正文的顺序。Graph 把这种秩序变成可审查的边——如果蓝图没完成，generation 节点在图中就根本没有入口边。它不把规则变成无限自由协商，而是把规则变成结构。`humanizer-zh` 仍然不改变路由，它只会在阶段 05 的质量节点提供语言判断。本阶段可以为 quality 节点预留入口，但不要在本阶段做完整的返工循环。

Graph State 的字段设计有一个核心原则：State 只保存 Run ID、当前节点、Artifact 引用、批次指针、审批状态和有限循环计数，正文从 Artifact 按需读取，Context Pack 只装当前角色所需的事实。如果你把正文全文放进 State，图会变得臃肿且难以序列化，而且你实际上是在用 State 代替 Artifact 的职责。

## 分步任务

本阶段的任务有一个自然的依赖关系：先定义 State，因为节点和边都依赖 State 的结构；然后映射节点和边，因为批次和 Context 都依赖图的拓扑；最后限制循环，因为循环的上限依赖你对整个流程的理解。不要跳过 State 直接写节点——那样你会不停地回头修改 State，浪费大量时间。

### 任务 1：定义 Graph State

写出最小字段——必须能解释当前节点、必须能解释下一条边、不能复制所有 Artifact 正文、不能承载前端展示文案。完成定义是状态可序列化且小，证据是 State 单测，确认它不会因为某次 Run 的正文特别长而膨胀。

### 任务 2：把七步映射为节点

每个节点调用阶段 03 的对应角色——节点先读取输入 Artifact，验证输出，写入 Artifact 与 Event，返回最小状态更新。完成定义是节点没有隐藏的下一步决定——它只返回自己的结果，不决定"接下来该走哪条边"。证据是节点测试，确认每个节点只做自己该做的事。

### 任务 3：写条件边与门禁

质量通过不等于自动发布——release 进入等待人工，停止进入终态，修订请求进入明确分支，未知条件进入错误终态。完成定义是所有边都有穷尽的测试，没有"默认继续"这种模糊的路由。证据是路由矩阵，覆盖所有条件组合。

### 任务 4：实现 Batch plan

Blueprint 产生章节顺序，Batch plan 把章节分批，每批有稳定 ID 和输入 Artifact 引用，每批完成后更新连续性台账。完成定义是失败批次不伪造后续完成——如果第一批失败了，第二批根本不应该被调度。证据是两批夹具，一批成功、一批失败。

### 任务 5：实现 Context Pack

Mission 节点只读 Intake，Blueprint 节点读 Mission 和来源摘要，Writer 节点读本章 brief、前置章节摘要和连续性台账，Quality 节点读候选与量规。明确长度预算，明确裁剪规则——不是"尽量少传"，而是"传什么、不传什么、为什么"有明确的规则。证据是 Context Builder 测试。

### 任务 6：限制循环

循环必须有最大批次数、必须预留最大返工次数（为阶段 05 做准备）、必须记录退出原因。循环超过界限必须升级人工。完成定义是不会无声无限运行——如果你把上限设成 100，图就应该在 100 次之后停下来并报告原因。证据是上限测试。这个任务看似简单，但它保护的是系统最基础的可靠性——一个不会停下来的系统，和没有系统没有区别。

## 关于 Graph 设计的补充说明

LangGraph 是一个强大的框架，但在这个项目里，它的角色是"受控 Workflow 的执行引擎"，而不是"多 Agent 自由协商的平台"。理解这个区别，才能避免把 Graph 做得过于复杂。

**State 的最小化原则。** Graph State 只保存执行控制所需的最小信息：Run ID、当前节点、Artifact 引用、批次指针、审批状态、循环计数。正文全文、课程内容、Skill 文本都不应该进入 State。如果你发现 State 里有一个字段叫 `mission_text` 或者 `blueprint_markdown`，那就是设计问题了——这些内容应该从 Artifact 按需读取，而不是在 State 中复制一份。State 越大，序列化和 checkpoint 的成本越高，出错的概率也越大。

**边的穷尽性。** 每一条从节点出发的边，你都需要考虑所有可能的目标状态。成功去哪、失败去哪、需要人工去哪、未知状态去哪——四个分支，缺一不可。如果某个节点只有"成功"和"失败"两条边，那你需要确认：这个节点真的不可能遇到需要人工介入的情况吗？如果不是，你需要补上第三条边。边的穷尽性不是形式主义——它是你唯一能保证图不会在运行时进入未定义状态的手段。

**Context Pack 的裁剪策略。** 不是"尽量少传"，而是"只传当前角色完成任务所必需的事实"。Mission 节点只需要 Intake，Blueprint 节点需要 Mission 和来源摘要，Writer 节点需要本章 brief、前置章节摘要和连续性台账。如果你不确定某个信息是否必要，先不加。如果需要，后续的 Finding 会告诉你"上下文不够"。这比一开始就传全部信息要好——过度传上下文的问题很难被发现，而上下文不足的问题会以明确的失败形式暴露出来。

**批次 ID 的稳定性。** batch_id 必须在 Blueprint 阶段就确定，并且在整个 Run 中保持不变。不要用批次索引（第 1 批、第 2 批）代替 batch_id——如果 Blueprint 被修改后重新生成，索引可能变化，但 batch_id 应该反映的是"这批章节的逻辑分组"。一个稳定的 batch_id 让你可以在阶段 06 的 checkpoint 恢复中准确找到"上次执行到哪一批"。

### 关于测试策略的说明

本阶段的测试需要覆盖"静态"和"动态"两个维度。静态测试验证图的定义是否正确——节点是否都有定义、边是否穷尽、State 是否不包含冗余字段。动态测试验证图的运行是否正确——正常路径是否按预期流转、失败路径是否停在正确的节点、审批门禁是否真的阻止了自动流转、批次失败是否阻止了后续批次。静态测试可以快速运行，适合在每次修改图定义后立即执行；动态测试需要完整的 Runner 环境，适合在阶段性完成后执行。两者缺一不可。

## 常见跑偏方式

把 LangGraph 当成多 Agent 自由聊天框架——在这个项目里，Graph 是控制流，不是对话流。把所有数据库记录塞进 State。让 Context Pack 永远加载全部课程。用批次索引代替稳定的 batch_id。在 release 前自动调用发布节点。为每个细节创建一个节点，导致图无法读懂。只测正常边，不测拒绝和未知边。这些偏差都会掩盖控制权——你会以为自己有一个受控的图，实际上它和 V0 的函数串联没有本质区别。

这些跑偏方式背后有一个共同的根源：把 LangGraph 当成了一个"更高级的函数调用库"。Graph 的价值不在于它能让代码看起来更整洁，而在于它把控制流变成了可审查的一等公民。如果你只是把函数调用换成了节点调用，但没有定义穷尽的条件边、没有限制上下文、没有给循环设置上限，那你和 V0 的函数串联没有本质区别——你只是换了一个更复杂的语法来做同样的事情。

## 完成后的系统快照

七步有了显式的控制流，角色只获得最小上下文，多章生成有了批次和连续性，人可以在 release Gate 接管。质量仍然只是一个入口，任务仍然由当前进程运行。下一步要把质量从一句摘要变成有证据的闭环——那是阶段 05 的故事。

每个阶段都是在前一个阶段的基础上建立起来的。你现在做出来的东西，会成为下一阶段的起点——好的起点让你事半功倍，模糊的起点让你举步维艰。花几分钟确认你真的理解了本阶段的每一个设计决策，然后带着信心进入下一阶段。

## 下一阶段门槛

每个节点、边、批次和 Context Pack 可解释，审批、异常和循环上限都有测试，技术方案冻结 Graph 状态、节点边、批次和 Context 契约。满足后进入[阶段 05](05-quality-loop-with-humanizer.md)，让质量从"模型说通过"变成"有证据的闭环"。
