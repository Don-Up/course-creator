# 阶段 01：先跑通七步 Happy Path V0

**预计投入：** 6 至 10 小时。

**一句话目标：** 用 React、FastAPI 和 Fake Provider 第一次让课程从输入走到人工 release，亲眼看到七步完整运转。

**这不是终态：** V0 故意没有可靠持久化、没有图恢复、没有真实质量闭环、没有独立 Worker。它的脆弱是教学计划的一部分，不是你没做好。

## 你将完成什么

这是整个项目里最激动人心的一个阶段。前面你花了两到四个小时画责任图，现在你要让那张图真的跑起来。用户输入一个最小的课程需求——可能只是一个主题、一个受众、一个目标——然后点击开始，页面会依次显示七个阶段的进度：intake 接收需求，mission 生成任务定义，blueprint 画出章节结构，batch_plan 安排生成顺序，generation 产出最小 Markdown 正文，quality 完成最小检查，最后停在 release，等待用户亲自选择"准备发布"还是"停止"。

每一步都有可见的输入摘要和输出摘要。如果某一步失败了，页面不会假装成功，而是停在失败的那一步，告诉你发生了什么。Fake Provider 为所有不确定的步骤返回固定的、可重复的结果，所以你不需要接真实模型就能验证整个流程。Mission 会显示课程目标和受众，Blueprint 会显示一到两个章节的结构，Batch plan 会显示生成顺序，Generation 会产出最小 Markdown 正文，Quality 会显示最小检查结论。整个流程中，系统不会把 API 的成功响应写成"已经发布"——发布权永远在人的手里。

## 你现在站在哪里

阶段 00 只建立了一份纸上的责任契约。现在你要把这份契约变成一条可见的纵向切片——从用户输入一路贯通到人工 release。这条切片优先证明产品形状，不优先证明生产可靠性。V0 可以在一个轻量 Runner 中串行执行，可以临时把状态保留在进程内，可以只有一门极短课程，可以只有一个批次。但它必须显式经过全部七步，不能把 Blueprint 和 Batch plan 隐藏在一个"生成中"的动画里，不能把 Quality 和 Release 合并为"完成"，不能让 Provider 返回的文本直接等于发布内容。

## 本阶段替换什么问题

传统做法会先建数据库、先建队列、先搭抽象图引擎，学员要等很久才第一次看见完整 Agent。这个阶段用一条短而完整的流程替换这种学习断层——先拿到完整产品形状，再逐个加固。

V0 的每一个"偷懒"都是后续阶段的教学动机：

| V0 的脆弱处 | 暴露的问题 | 后续解决阶段 |
| --- | --- | --- |
| 状态在内存中 | 刷新或重启即丢失 | 阶段 02 持久化事实 |
| 一个 Prompt 包办一切 | 规则、角色、权限混在一起 | 阶段 03 角色分离 |
| 函数按固定顺序串联 | 没有显式路由和恢复 | 阶段 04 LangGraph |
| 一句"质量通过" | 没有可追溯的质量证据 | 阶段 05 质量闭环 |
| 同步执行长任务 | 进程崩溃即丢失执行权 | 阶段 06 Worker |
| 一次成功演示 | 没有恢复和人工路径证据 | 阶段 07 交付治理 |

这不是设计缺陷，而是教学起点——每个脆弱处都在告诉学员"这里需要加固"，而不是"你做错了"。

## 两份 Skill 在本阶段的角色

`teach-generator` 给 Mission、Blueprint 和正文提供最小规则。Mission 必须包含受众、学习目标、范围和停止条件，Blueprint 必须先于正文产生，Generation 不应跳过课程结构，Quality 至少保留"不是生成文件就完成"的原则。`humanizer-zh` 只在 Quality 的演示 Gate 参与——它可以返回一条语言风险说明，可以建议一段文本需要编辑，但它不应改写事实源、不应取代任务定义、不应批准 release。V0 可以用规则摘要模拟 Skill 读取，但不可以假装已完整执行所有 Skill 内的质量脚本。这个区分很重要：你是在跑通流程，不是在假装产品已经做完。

## 五类边界

| 范围 | 本阶段要做 | 本阶段不做 | 理由 |
| --- | --- | --- | --- |
| 前端 | 表单、七步状态、最小结果和 release 决策 | 完整工作台、历史检索 | 先让流程可见，再考虑管理 |
| 后端 | 一个 V0 开始接口与运行摘要接口 | 完整领域 API、长期任务 | 先实现切片，再考虑完整 |
| 数据/文件 | 最小 Markdown 结果可临时保存或返回 | 版本血缘、正式表设计 | 阶段 02 再落账 |
| 运行时 | Fake Provider 与轻量 Runner | LangGraph、Worker、真实 Provider | 控制不确定性，先证明形状 |
| 测试 | 正常、Provider 失败、release 未决定 | 恢复、竞争、质量修复 | 当前只证明形状 |

这几条边界背后有几条原则：前端只展示 Runner 给出的状态，Runner 不应信任前端传来的"已完成"，Fake Provider 应能固定返回成功或指定失败，release 的默认状态应是等待人工决定而不是默认批准。这些原则在 V0 里看起来是小事，但它们保护的是后续阶段不会在错误的基础上继续堆代码。

## 最小流程图

```text
React form
  -> POST /v0/course-runs
  -> V0 runner
  -> intake
  -> mission
  -> blueprint
  -> batch_plan
  -> generation
  -> quality
  -> WAITING_FOR_RELEASE
  -> React release action
  -> READY_FOR_RELEASE or STOPPED
```

每一箭头都应有可观察摘要。成功路径不应跳过 quality，失败路径不应进入 release 成功状态，人工未选择时不应有发布结果。这条流程看起来简单，但它是整个系统最核心的骨架——阶段 02 到 07 的所有工作，都是在加固这条骨架，而不是替换它。

## 最小对象

`CourseInput` 是用户输入，`V0Run` 是一次临时执行摘要，`StageRecord` 是单步可见状态，`MissionDraft` 是任务定义候选，`BlueprintDraft` 是章节结构候选，`BatchPlanDraft` 是生成顺序，`LessonDraft` 是候选正文，`QualitySummary` 是最小质量结论，`ReleaseDecision` 是人的决定。这些名称在你的实现里可以不同，但这些职责不能混在一个无类型的字典里——如果什么都不分，后面阶段每次改动都会是一次冒险。

## 分步任务

### 任务 1：定义 V0 输入和七步状态

完成定义是输入字段和七个状态名称在前后端一致。先写状态转换的纯函数测试——不需要跑完整流程，只需要验证状态从一个阶段到下一个阶段的规则是否正确。输入只保留课程主题、受众、目标和语言，不要先加入来源上传、多用户或权限。证据是状态转换测试与页面截图。常见误区是前端自造第八个"done"业务阶段，把 release 之后的状态和七步本身混在一起。

### 任务 2：实现 Fake Provider

完成定义是每个不确定节点有固定成功输出，同时还要有可触发的失败输出。失败开关可以通过请求参数或测试夹具控制，这样你可以在不修改代码的情况下验证失败路径。不要接真实模型密钥，不要让随机文本破坏断言。证据是 Provider 单测——成功和失败都要覆盖。这个 Provider 会伴随你好几个阶段，把它做好，后面的验证会省很多事。

### 任务 3：实现轻量 Runner

完成定义是 Runner 按七步依次调用最小函数，每步在进入和完成时更新 `StageRecord`，每步失败时保存可解释的错误摘要，在 release 前停止自动流转。不要在这个 Runner 中预建队列——那是阶段 06 的事。证据是一条完整运行记录，从 intake 到 release 等待状态。常见误区是让 Runner 在失败后继续执行后续步骤，或者把失败信息写成"出错了"三个字，丢掉了所有排查线索。

### 任务 4：实现最小 API

完成定义是可以开始一次 V0 Run、可以读取当前摘要、可以提交 release 决定。API 只返回可序列化对象，不返回 Provider 的隐藏提示词。证据是请求和响应样例——正常路径、失败路径和 release 的三种决定（准备发布、停止、未决定）都要覆盖。

### 任务 5：实现 React 可观察界面

完成定义是用户可以看到七步状态、可以查看 Mission、Blueprint 和 Markdown 摘要、release 只有在质量步骤结束后才可点击。失败时显示失败在哪一步，而不是一个笼统的"失败了"。不要把所有结果塞入一个弹窗——七步的信息密度需要用适当的布局来承载。证据是正常和失败截图，至少各一张。

### 任务 6：留下 V0 限制清单

完成定义是每个便利做法都有对应的后续替换阶段。列出内存状态限制（刷新即丢失）、单 Prompt 限制（规则混在一起不可审查）、顺序函数限制（没有路由和恢复）、最小质量限制（没有 Finding 和修复闭环）、同步执行限制（API 进程跑长任务）。证据是技术方案的"已知限制"小节。这份清单不是你的失败记录，而是你之后五个阶段的任务清单。

## AI 交付后的人类 Review

AI 交付代码之后，你打开页面，亲自走一遍。确认页面上真的出现了七个步骤，不是一个百分比进度条。确认 Mission 和 Blueprint 在 Generation 之前就产生了——如果你看到的是先生成正文再补蓝图，那就是顺序错了。确认 Batch plan 不是隐藏状态，确认 Quality 不等于 release，确认 release 没有默认自动批准，确认 Fake Provider 可以稳定复现失败。最后检查 API 有没有偷偷藏入真实模型调用，确认 V0 的已知限制被明确写在了技术方案里。


### 遇到验收问题时

如果你在验收时发现七步不按顺序显示、Fake Provider 结果不稳定、失败后系统仍进入 release 或用户停止后显示已发布——不要直接让 AI"修一下"。先自行检查当前 V0 Run 的七步摘要、请求响应、Fake Provider 模式、测试输出和浏览器网络请求。然后让 AI 判断问题更可能在输入 Schema、状态转换、Runner 顺序、Provider 夹具、API 序列化、React 投影还是 release 控制。确认根因后再给最小修复，并要求修复计划包含回归测试且说明不会提前引入哪个后续机制（SQLite、LangGraph、Worker 等）。

## AI 做完后重点关注什么

从页面逐步对照 Runner 输出，确认七步不是视觉装饰——每一步真的在 Runner 里执行了，不只是前端动画。尤其检查 quality 和 release 之间是否仍有一个真实的人类决定，而不是代码自动走到了 release。把 V0 的内存和同步限制写进证据记录，这些是你之后五个阶段的任务清单。

## 验收关卡

### 自动化关

运行 V0 Runner 状态转换测试。运行 Fake Provider 成功与失败测试。运行 API 开始、读取和 release 决定测试。运行前端构建。运行课程契约检查。

```bash
apps/api/.venv/bin/pytest -q apps/api/tests
npm --prefix apps/web run build
npm run test:contract
```

### 正常路径

输入一个小主题，提交 V0 Run，逐步观察从 intake 到 quality 的每一步。检查 Mission 是否包含受众和目标，检查 Blueprint 是否先于 Markdown 出现，检查 Batch plan 是否显示章节顺序，检查 Markdown 是否来自 Fake Provider，检查 quality 是否显示语言 Gate 摘要。在 release 点击"准备发布"。保存 Run 摘要和页面截图。

### 失败路径

用失败 Fake Provider 让 generation 出错，确认错误显示在 generation 这一步，确认 quality 和 release 不会假装成功。然后重新开始一次成功 Run，在 release 点击"停止"，确认状态显示停止而非发布。保存响应、截图和测试输出。

### 解释关

为什么 V0 必须显式显示 Batch plan，不能把它藏在"生成中"？为什么 Fake Provider 比真实模型更适合这一阶段的主验收？为什么 quality 之后还需要 release，不能直接在 quality 里自动发布？V0 刷新后丢失状态为什么不是可以忽略的小缺陷，而是后续阶段必须解决的核心问题？

## 常见跑偏方式

把七步压缩成"提交、生成、完成"三步，让 generation 直接写最终发布文件，在 Provider 内决定下一步流程，在质量失败后仍自动进入 release，把 Humanizer 的语言意见当成课程真相，为了所谓真实感立刻接入模型密钥，为了所谓架构完整立刻引入数据库和队列，为了好看只做动效不显示每步结果。这些偏差都会抹掉后续阶段的学习动机——如果 V0 看起来已经"做完了"，你就不会觉得有必要引入持久化、角色分离、Graph 和质量闭环了。

## 完成后的系统快照

你拥有一个真实可跑的七步雏形。它可以从输入生成最小课程，可以展示失败，可以等待人工 release。它仍然脆弱——刷新或重启可能丢失事实，Prompt 和角色仍未真正分离，流程尚未成为可恢复图，质量还没有 Finding 和修复闭环，长任务仍不应进入生产。但你已经看到了完整的形状，这是最重要的。

## 下一阶段门槛

七步在页面和后端摘要中一致，成功、Provider 失败和用户停止都可以重复观察，release 只由人决定，技术方案已留下 V0 限制清单。满足后进入[阶段 02](02-durable-facts-and-run-workbench.md)，开始让事实落地。
