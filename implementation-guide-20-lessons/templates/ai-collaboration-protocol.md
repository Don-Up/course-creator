# AI 协作协议

每个阶段都有一份完整的提示词，你直接复制粘贴给 Coding Agent 即可。提示词里已经包含了"先分析、再实施"的完整逻辑——Agent 会先读代码、分析方案，确认后再按编号顺序逐一实现。你不需要自己拆分任务，也不需要手动分两次发送。

## 使用原则

- 在你的学员仓库中实现，不要在完整 Demo 中修改或复制。Demo 是参考地图，不是你的起点。
- 保留工作区既有改动，不要让 Agent 擅自回退无关文件。Agent 有时候会自作主张地"清理代码"，你需要在提示词里明确禁止。
- 一次只处理当前阶段，不要跳过——每个阶段都依赖前一阶段的成果。
- Agent 的完成声明不是证据；测试通过、请求返回正确结果、SQLite 查询一致、页面截图才对得上，这些才是证据。
- 真实模型调用可以用于冒烟，但核心验收必须能用 Fake Provider 重复。如果你发现某个测试今天通过明天失败，大概率是因为你用了真实模型而不是 Fake Provider。

## 提示词结构

每个阶段的提示词都包含以下固定部分：

1. **背景**：当前仓库里有什么、处于什么状态。
2. **阶段目标**：这个阶段完成后用户能看到什么。
3. **技术栈**：本次引入的框架、类库或工程解法，以及每项解决什么问题。
4. **硬约束**：绝对不能做的事——比如不能引入后续阶段的能力、不能破坏已冻结的契约。
5. **先分析**：Agent 必须先读代码、回答几个设计问题，确认方案后再动手。
6. **再实施**：按编号顺序逐一完成的任务，每完成一项跑测试再继续。
7. **技术方案**：阶段完成后留下的设计决策记录。
8. **报告格式**：Agent 汇报结果的固定格式。

你不需要自己写提示词——每个阶段的文档里都有一份完整的，直接复制即可。

## AI 完成后由学员亲自验收

Agent 完成之后，你才是最终的验收者。不要跳过下面任何一步：

1. 运行阶段的自动化命令，记录真实的 `PASS`、`FAIL` 或 `NOT RUN`。`NOT RUN` 必须写明真实环境原因——"环境没准备好"是原因，"应该能通过"不是。
2. 按"学员验收步骤"完成正常与异常场景，保留响应、截图或标识。不要只跑正常路径——失败路径往往比正常路径更能暴露问题。
3. 阅读 Agent 改动过的依赖、配置、迁移或启动文件，能说清它们的用途与失效表现。如果你看不懂某个依赖是干什么的，先查清楚再继续。
4. 从阶段指定入口追一遍调用链，写下事实在哪里落账、谁拥有状态转换权。如果你追到一半发现断了，那就是问题。
5. 失败时先保存证据，再使用阶段文档中"AI 交付后的人类 Review"部分的排障指引。不要用"再修一下"替代问题描述——Agent 需要知道具体哪里不对，不是"还是不行"。
6. 回答解释关的问题，确认自己真的理解了，再进入下一阶段。
