# AI Course Studio：从两份 Skill 到七步 Agent —— 一份 Vibe Coding 实战指引

欢迎。如果你刚学完 AI Course Studio 的课程，正对着一个空仓库发愁——不知道第一行代码该写什么，不知道什么时候该引入 LangGraph，也不知道怎样才算真正"做完了"——这份指引就是为你准备的。

我们不会从数据库设计开始，也不会从脚手架配置开始，更不会让你先把所有课程章节重读一遍再动手。我们会从项目里真实存在的两份 Skill 出发：`.agents/skills/teach-generator/` 与 `.agents/skills/humanizer-zh/`。你的第一个目标不是搭基础设施，而是让 React、FastAPI 和 Fake Provider 一起跑通一个完整的七步课程生产 Agent——哪怕它还很粗糙，哪怕它跑在内存里，哪怕它只生成一章。当你亲眼看到课程从需求走到正文的那一瞬间，后面每一步要加固什么、为什么加固，都会变得清晰得多。

## 这份指引解决什么问题

很多人在学完课程之后会做同一件事：把 LangGraph、SQLite、Worker、质量系统、Context Pack 一次性丢给 Coding Agent，然后等上半天，得到一个看起来能跑但完全不知道内部发生了什么的东西。这不是你的问题——传统工程教学习惯从底层往上搭，但 Vibe Coding 的节奏恰恰相反：你应该先看见完整的产品形状，再逐个替换它最脆弱的部分。

所以我们把开发顺序反过来，从完整形状开始，一步步加固：

```text
两份 Skill 的规则地图
-> 七步 Happy Path V0
-> 持久化事实与工作台
-> 角色、Skill 与 Artifact
-> Graph、Context 与批次控制
-> 质量闭环
-> 可恢复执行与人工控制
-> 交付治理与迁移复盘
```

AI 可以生成代码、运行测试、给出诊断建议，但它不替你决定哪些数据是事实源，不替你设计状态转换，不替你分配权限，更不替你按下发布按钮。这些判断是你的，也只能是你的。

## 三类材料与各自的职责

在开始之前，我们先把三样东西的关系说清楚，因为后面每个阶段都会反复用到它们：

| 材料 | 用来回答什么 | 不要用来做什么 |
| --- | --- | --- |
| [PRD](../../../assets/aiagent/PRD.md)、[FE TD](../../../assets/aiagent/FE-TD.md)、[BE TD](../../../assets/aiagent/BE-TD.md) | 用户目标、领域术语、状态、事实源与系统边界 | 从文档猜函数名或复制目录 |
| [20 章课程](../lessons/) 与 [项目学习指引](../../../course-learning-guide.md) | 一个机制为什么存在、何时需要它、怎样理解代码 | 替代实现和验收 |
| 当前 AI Course Studio Demo | 最终用户行为、职责划分和代码阅读入口 | 逐行复制代码、强迫自己的目录一致 |

我们在未来会提供一个薄统一脚手架，里面只有 React + FastAPI 的最小工程壳、Fake Provider、测试入口和两份 Skill。它不会偷偷帮你建好 Course、Run、Workflow 或 Artifact——那些是你自己要在八个阶段中一步步实现的。

## V0 如何逐步加固：一张替换路线图

阶段 01 的 V0 会故意留下很多"便利但不安全"的做法，这不是设计缺陷，而是教学起点。下面这张表告诉你每个便利做法将在哪个阶段被替换，以及你最终应该能解释的改进是什么：

| V0 的便利做法 | 后续替换阶段 | 学员应能解释的改进 |
| --- | --- | --- |
| 用一个 Runner 和页面变量保存所有临时结果 | 阶段 02 | 事实、历史和投影可以在刷新和重启后查询 |
| 用一个巨大 Prompt 混合任务定义、蓝图、写作和审查 | 阶段 03 | 角色、Skill、Schema 和 Tool 可以独立审查和修改 |
| 函数按固定顺序互相调用，没有显式路由 | 阶段 04 | Graph、审批、批次和上下文有明确的控制者和边界 |
| 一句"质量通过"就结束检查 | 阶段 05 | Finding、Candidate、Verification 和预算构成可追溯的质量证据 |
| API 进程直接跑完整条长任务链 | 阶段 06 | Command、Worker、lease 和 checkpoint 支持崩溃接管和人工干预 |
| 一次成功演示就认为项目完成 | 阶段 07 | 正常、恢复和人工三条路径形成完整的交付结论 |

## 课程章节与项目阶段为何不是一对一

课程按概念讲解组织，项目按可交付能力组织，因此阶段会引用多个、甚至不连续的章节。这是刻意设计，不是目录没有整理好。当你实际动手做的时候，你很少会按课本顺序来解决一个工程问题——一个阶段往往需要同时理解好几个分散在不同章节里的概念，然后把它们组合在一起。

每个阶段都把材料分为三类：

- **本阶段必读**：开工前必须理解的 2 至 4 章。
- **实施时查阅**：做某一小任务时按需打开的章节。
- **完成后回看**：验收后用于复盘和为下一阶段做准备的章节。

举个例子：阶段 01 用第 01、02、19 章先跑出完整七步 V0；阶段 05 则同时需要 `teach-generator` 的三级质量规则、`humanizer-zh` 的语言判断、第 13 章的有界循环与第 13 章的 Finding/Repair。这些内容在课程里分属不同章节，但在这个项目里，它们必须一起工作才能形成一条真正可验收的质量闭环。

## 每个阶段的固定学习循环

每个阶段我们都遵循同一条学习循环，它会帮你养成与 Coding Agent 协作的肌肉记忆：

1. 先读本阶段的"你现在站在哪里"和"学习导航"，搞清楚当前系统的真实能力和已知弱点。
2. 写出自己的验收清单，包括自动化命令、正常路径和至少一个失败或降级场景。
3. 复制本阶段的**规划提示词**发给 AI，要求它先分析、先计划，但不许改代码。这个阶段你要审查 AI 是否理解了事实源、状态转换和非目标。
4. 确认 AI 的计划靠谱之后，复制**实现提示词**，一次只完成一个小任务，跑完验证再继续下一个。
5. 按"学员验收步骤"亲自操作一遍，正常路径和失败路径都要走。遇到问题，用**排障提示词**附上证据再求助。
6. 沿着"AI 做完后重点关注什么"的入口去读代码，不要只看 AI 的完成报告。
7. 要求 AI 留下本阶段的**技术方案**：选型理由、模块边界、状态和数据流、失败处理、测试证据、已知限制和下一阶段的冻结契约。
8. 填写[阶段证据记录](templates/stage-evidence.md)，诚实判断自己是否达到了进入下一阶段的门槛。

关于怎么和 AI 协作、怎么写提示词、怎么验收，通用的写法和行为准则都写在[AI 协作协议](templates/ai-collaboration-protocol.md)里了，每个阶段都会用到。

## 阶段文档标准

每份阶段文档都包含以下固定模块：两份 Skill 的职责描述、课程三级阅读地图、前端/后端/数据文件/运行时/测试的五类边界卡片、分步任务、规划/实现/排障三类提示词、人类 Review 清单、正常与失败验收关卡、解释关问题，以及下一阶段的冻结契约。每份文档不少于 300 行，内容必须具体可执行，不用空行或重复标题来凑数。

## 如何正确参考当前 Demo

当前仓库里有一个完整的 AI Course Studio Demo，它对你来说是一张行为和职责的地图，而不是一份标准答案。对照它的时候，优先问这四个问题：

- 这个入口接收什么意图，返回什么结果？
- 这个对象是当前事实、不可变历史、读取投影，还是内部恢复状态？
- 哪一层有权改变状态、写文件、调用模型或批准发布？
- 出错、重试、重复执行或页面刷新时，系统如何证明自己没有丢失或伪造事实？

你自己的组件命名、模块划分、迁移版本和辅助函数都可以和 Demo 不同——这完全没问题。但以下内容绝对不能静默不同，因为它们是领域契约，不是实现细节：

- API 和领域对象的语义；
- 状态转换与人工决策的含义；
- Artifact、Snapshot、Event 与 Checkpoint 的职责；
- 重复、失败、恢复、质量与发布的可观察行为。

阶段中的"Demo 阅读地图"会指出该看什么，也会明确此时不要提前复制什么。

## 三层验收与阶段证据

每个阶段必须同时通过三层验收才算完成。缺一层都不算。

1. **自动化关**：规定的测试、typecheck、build 或专项脚本已经实际执行过，并且你知道结果是什么。
2. **学员验收步骤**：你亲手完成了正常路径的操作；从阶段 02 开始，每一阶段还必须额外完成一个失败、重复、降级或恢复场景。
3. **解释关**：你能用自己的话说明：事实存在哪里、谁有控制权、失败会怎样收敛、证据放在哪里。

这里有一条铁律：永远不要写"应该通过"。命令有没有运行、实际输出是什么、环境是不是被什么东西挡住了、截图、API 响应、Run ID、Artifact 版本和日志关联信息——这些都应该如实写进[阶段证据记录](templates/stage-evidence.md)。Agent 的完成声明不是证据，你亲手跑出来的结果才是。
