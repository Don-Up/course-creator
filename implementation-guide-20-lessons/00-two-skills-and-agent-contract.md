# 阶段 00：从两份 Skill 画出 Agent 契约

**预计投入：** 2 至 4 小时。

**一句话目标：** 不写一行课程业务代码，先把 `teach-generator` 与 `humanizer-zh` 变成七步产品流程中可审查的规则，让后续每一个阶段都有共同的契约参照。

**这不是终态：** 此时你没有 Course、没有 Run、没有 Workflow，也没有任何课程正文。你只有一份画在纸上的责任图，但它会是你之后所有实现决策的地基。

## 你将完成什么

这个阶段结束时，你会得到一份自己的责任图——不是从 Demo 里抄来的，是你读了两份 Skill 之后亲手画出来的。这份图里必须有七个用户可见的阶段，它们依次是 `intake`、`mission`、`blueprint`、`batch_plan`、`generation`、`quality`、`release`。每一步你要标出它接收什么输入、产出什么输出、谁拥有下一步的决定权，以及失败时用户能看到什么。

你会把两份 Skill 放进正确的位置——`teach-generator` 约束任务定义、蓝图和正文规则，`humanizer-zh` 在 quality 阶段作为中文表达的编辑 Gate。你不会把 Skill 命名成顶层 Agent，不会把 Humanizer 当成事实核验器，也不会因为未来要使用 LangGraph 就在本阶段开始搭图。这份责任图可以是一份 Markdown 文档，可以是你仓库里的设计笔记，形式不重要，重要的是它必须能被另一位同学读懂，并且能解释清楚这个系统为什么不是"一次模型调用"就能完成的事情。

## 你现在站在哪里

你的起点是两份真实存在的领域规则，除此之外什么都没有。理解这两份 Skill 的边界，是之后所有设计决策的前提。

`teach-generator` 规定了课程生产应该如何开始、如何规划、如何写作、如何检查、如何返工和如何人工审核。它要求先读取任务约束与课程 workspace，要求把来源政策、学习者背景、学习目标和停止条件写成事实，要求课程蓝图先于批量正文，要求确定性检查、量规审查、Humanizer、回归检查和人工审核形成质量闭环。它是一套生产规则，不是一个黑盒函数。

`humanizer-zh` 规定了中文学生可见文本如何避免机械、宣传、套话和翻译腔。它帮助编辑表达，但它不确认外部事实、不选择课程目标、不批准发布。它是一道语言质量 Gate，不是事实核验器。

理解这两份 Skill 之后，你还需要理解一组更基础的区分：Skill 没有独立的产品入口，也不拥有数据库状态；Agent 是在明确目标、状态、可用工具与停止条件下完成任务的执行角色；Workflow 负责顺序、门禁、路由和恢复边界；Tool 负责被授权的具体能力；而人保留任务确认、风险升级与发布决定。这一层区分看起来很抽象，但它是之后所有实现决策的地基——如果这里混淆了，后面每一阶段都会在错误的基础上堆代码。

## 前置版的风险

在没有这张图的情况下，Coding Agent 有一个非常常见的做法：它会创建一个叫 `CourseAgent` 的东西，把两份 Skill 的文本全部拼进一个巨大的 Prompt，让模型自行决定下一步该做什么。然后它会用"文字读起来自然"来证明"课程内容正确"，用 HTTP 200 来证明"课程已发布"，用页面上的进度条来证明"运行事实已落账"。它在没有批准的情况下写文件，遇到失败时只能重跑全部流程，而且你完全不知道问题出在哪一步。

这些问题不是提示词再长一点就能修复的，它们来自一个根本原因：责任没有被分开。本阶段用规则归属表和七步产品契约来替换这种模糊，让每一种决策都有一个明确的所有者。

## 两份 Skill 在本阶段的角色

### `teach-generator`

你要读取这份 Skill 的启动规则、任务定义规则和质量闭环规则——不是读全部，是读和本阶段有关的部分。把它视为课程生产的领域规则来源，记录它要求的任务事实、workspace 文件、对来源和版本敏感事实的限制、对蓝图、批次和正文的先后要求，以及它要求人工审核的位置。不要在本阶段复制它的全部目录结构，不要把它的建议字数变成硬编码产品规则，更不要把它当成一个可以随意调用的黑盒函数。它是一份规则文档，你读它，理解它，然后把它翻译成责任图上的约束。

### `humanizer-zh`

你要读取它的核心规则速查和文本模式，把它视为中文学生可见文本的编辑 Gate。记录它能发现的表达类问题——比如宣传腔、翻译腔、三段式套话、AI 高频词汇——同时记录它必须保留原意的边界。它不能替代来源证据，不能替代教学设计量规，不能替代构建检查，不能决定是否发布。它只能在正文候选版本形成之后参与质量判断或改写建议，而且它的判断本身也需要被验证。

## 先画五类边界

| 范围 | 本阶段要做 | 本阶段不做 | 原因 |
| --- | --- | --- | --- |
| 前端 | 画出用户能看到的七步和 release 决定 | 不实现页面 | 先定义观察对象，再考虑渲染 |
| 后端 | 画出 API 将来负责受理与读取的位置 | 不实现接口 | 先定义控制权，再考虑传输 |
| 数据/文件 | 列出未来 Mission、Blueprint、Artifact 的事实类别 | 不建表、不写文件 | 先防止混淆事实，再考虑存储 |
| 运行时 | 说明 Provider、Agent、Workflow、Skill 的关系 | 不接真实模型、不跑图 | 运行策略尚未确定，先确定边界 |
| 测试 | 写出未来每一步要留下的证据 | 不补业务测试 | 尚无业务行为，先定义证据类型 |

这五类边界背后有几条原则，值得单独写出来，因为它们会在后面每一个阶段反复出现：前端不是流程真相的所有者，后端接口不是长任务的执行者，数据库不是所有临时上下文的垃圾桶，workspace 不是页面状态的替代品，Provider 不是流程的决策者，Skill 不是权限系统，测试不是模型自我评价的同义词。每一条听起来都像常识，但在实际开发中，它们是被违反最多的几条。

## 最小责任图

```text
学员输入课程意图
        |
        v
intake ----> 接收、校验、展示待办
        |
        v
mission ---> teach-generator 约束任务定义
        |
        v
blueprint -> teach-generator 约束来源、结构和学习路径
        |
        v
batch_plan -> Workflow 决定批次与顺序
        |
        v
generation -> 受限写作角色按 Skill 生成候选 Artifact
        |
        v
quality ---> 确定性检查 + 量规 + humanizer-zh
        |
        v
release ---> 人决定继续、修改、停止或准备发布
```

`intake` 的输入是课程意图，它负责接收、校验并展示待办，但不确定任务是否完整。`mission` 的输出是可验收的任务定义，它用 `teach-generator` 的约束把模糊目标变成可检查的事实。`blueprint` 的输出是课程结构和证据需求，它确定来源、章节前置关系和教学路径，`research` 是它的内部活动，不需要单独成为一个顶层阶段。`batch_plan` 的输出是受控的生成批次，由 Workflow 而非 Provider 决定顺序。`generation` 的输出是候选课程 Artifact，由受限的写作角色按 Skill 生成。`quality` 的输出是证据化的通过、Finding 或升级请求，包含确定性检查、量规和 Humanizer。`release` 的输出是人的明确决定——继续、修改、停止或准备发布。每一步都应能解释失败，每一步都不能靠模型猜测前一步是否成功。

## 规则归属表

| 问题 | 正确所有者 | 错误所有者 |
| --- | --- | --- |
| 学员目标是否完整 | intake 与人工确认 | Writer |
| 课程任务如何写成可验收定义 | Mission 角色 + teach-generator | Humanizer |
| 章节结构是否符合前置关系 | Blueprint 角色 + teach-generator | 前端组件 |
| 每批写哪些章节 | Workflow | Provider |
| 生成正文的表达 | Writer 角色 + teach-generator | 数据库触发器 |
| 中文语气是否自然 | humanizer-zh Gate | 发布按钮 |
| 外部事实是否可用 | 来源政策和审查证据 | Humanizer |
| 是否继续返工 | 有界 Workflow + 人 | 无限模型循环 |
| 是否发布 | 人 | 自动 Prompt |

这张表在后续阶段会不断细化——当阶段 03 引入 Agent Definition 时，角色会变得更具体；当阶段 05 引入 Finding 时，质量判断会变得更可追溯。但它的核心归属关系不会被推翻，因为在设计层面，这些判断的所有者从一开始就是确定的。

## 分步任务

### 任务 1：读出两份 Skill 的输入和输出

完成定义是每份 Skill 都有"输入、规则、输出、禁止承担的责任"四行笔记。先读 `teach-generator` 的启动与质量段落，再读 `humanizer-zh` 的核心规则和边界。不要先读 Demo 实现来替 Skill 下定义——Skill 是规则的源头，Demo 是规则的实现，你应该先理解源头再对照实现，而不是反过来。你的证据是四行笔记本身，常见误区是把 Skill 的建议目录当成应用 API。

### 任务 2：写出七步产品契约

完成定义是每步都有输入、输出、所有者、失败可见结果。优先使用流程图或表格来表达，把 research 作为 Blueprint 的内部活动说明，不要额外创建第八个顶层阶段。你的证据是一条可以从 intake 追到 release 的完整箭头链。常见误区有两个：一是把 quality 和 release 合并成"完成"——它们是完全不同的两件事，quality 产生证据，release 产生决定；二是把每一步写成"模型自动完成"——七步中有多步需要人工参与，不是一条自动流水线。

### 任务 3：标出事实与控制权

完成定义是区分课程内容事实、运行历史、读取投影和临时执行状态。此时不要求为这些对象命名最终的数据库表，只要求写清"谁可以写、谁可以读、谁不可伪造"。你的证据是一张最小所有权表。常见误区是让 React state 成为 Run 的唯一来源——页面状态是投影，不是事实，刷新就没了。

### 任务 4：选择 V0 的最小工程壳

完成定义是写出 React、FastAPI、Fake Provider 与测试壳各自只承担什么。选择 React + TypeScript 用于可见进度与表单，选择 FastAPI + Pydantic 用于明确的请求和响应边界，选择 Fake Provider 让核心验收可重复，选择最少依赖——不提前加入向量库、MCP 平台或消息队列。你的证据是选型理由和非目标清单。常见误区是把薄脚手架描述成已经存在——它还没有，你只是在选择它将来应该长什么样。

### 任务 5：写下阶段冻结契约

完成定义是列出阶段 01 不能破坏的七步名称和责任边界。记录 release 必须有人工决定，记录 Humanizer 只是质量 Gate，记录 V0 必须使用 Fake Provider 做主验收。你的证据是"下一阶段冻结契约"小节。常见误区是只留下代码任务清单而不留下设计决定——契约保护的是设计意图，不是实现细节。

## AI 交付后的人类 Review

AI 交付责任图之后，你不要只看措辞是否漂亮。逐条检查：七步是否完整且顺序可解释？每一步是否有确定的责任者？规则是否被写成可读取的约束而不是人格化的角色？是否出现了"模型自行判断发布"的表述？Humanizer 是否被过度授权——比如让它核验外部事实或决定课程目标？是否混淆了课程内容事实、运行历史和页面投影？技术方案是否不是一句"用了 React 和 FastAPI"就结束了？技术方案是否留下了下一阶段的冻结契约？

## AI 做完后重点关注什么

重点读责任图本身，不要只看文字是否通顺。确认每个 Skill、角色、Workflow 与人类决定在图中都只有一个清楚的位置，没有重叠，没有遗漏。追问任何"模型自动决定"的表述——到底是谁授权了这个决定？如果授权方不明确，那就是一个需要修正的漏洞。

### 正常路径

拿一个具体的需求——"为零基础产品经理创建一门 AI Agent 课程"——从 intake 开始口述每一步。在 mission 说出任务定义应包含什么（受众、前置知识、学习目标、停止条件）。在 blueprint 说出来源和章节结构为何要先于正文。在 generation 说出 Writer 的可交付物是什么。在 quality 说出 Humanizer 在整个质量流程中的位置。在 release 说出人能做什么决定。保留这次口述的文字记录或表格截图。

### 失败路径

假设 Writer 提交了一段流畅但没有任何来源依据的中文正文。不要让 Humanizer 给它"通过"——Humanizer 只管表达，不管事实。说明应由哪个 Gate 产生什么 Finding。再假设模型建议自动发布，说明 release 为什么应该拒绝这个建议。保留这两个判断的文字证据。

### 解释关

Skill 与 Agent 的区别是什么？为什么 Workflow 而不是 Provider 决定 batch_plan 的下一步？为什么 Humanizer 不能替代来源审查？为什么 release 必须仍然由人拥有？这四个问题你必须能用自己话回答，而不是背诵定义。

## 常见跑偏方式

把两个 Skill 拼成一个系统 Prompt，把每个阶段都命名为一个 Agent，把 Tool 当成可自行决定业务目标的角色，把页面点击等同于事实已落账，把真实模型调用作为唯一验收手段。为了"先进"而提前引入多 Agent 自由协商，为了"完整"而在阶段 00 设计全量数据库，为了"顺滑"而取消人工 release。这些做法都会让下一阶段难以验证，因为它们把本应在不同阶段逐步引入的复杂性一次性堆在了一起。

## 完成后的系统快照

你还没有一个可运行的课程生产系统。但你已经有了可审查的产品契约——你知道两份 Skill 各自的责任，知道七步中每一步的责任，知道人不应交出的决定权，知道 V0 应该从完整产品形状而非基础设施堆叠开始。这些看起来是"纸上谈兵"，但它们是你之后不再迷失的关键。
