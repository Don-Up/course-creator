# 阶段 07：以证据交付，并判断何时迁移

**预计投入：** 6 至 10 小时。

**一句话目标：** 把一次成功、一次恢复和一次人工干预连成一份可审计的证据包，写下系统当前的边界，并诚实地判断什么时候才需要更复杂的架构。

**这不是终态：** 本地教学实现不是默认的生产方案。证据包的价值在于诚实——它记录了什么已经验证、什么没有验证、什么在当前规模下是安全的、什么在更大规模下会出问题。

## 你将完成什么

这是八个阶段里最特殊的一个。前面六个阶段你一直在"做"——搭事实层、拆角色、建图、做质量闭环、做可恢复执行。这个阶段你要停下来，回头看，把这段时间你做出来的东西变成一份别人也能读懂的交付证据。

你会交付三条完整的路径证据：一条 Happy Path，用 Fake Provider 从课程需求一路走到人工 release；一条失败或恢复路径，记录 Worker 崩溃后如何被接管、如何不重复 Artifact；一条人工控制路径，记录质量预算耗尽后如何升级人工、如何提交 STOP 或 REVISE。每条路径都可以关联到具体的 Course、Run、Command、NodeExecution、Artifact、Finding、Event 和 Trace。你会记录预算消耗——Provider 调用了多少次、返工消耗了多少、有没有超出阈值。你会检查敏感数据是否进入了日志或 Artifact，记录发布决定者是谁。最后，你会完成一次架构迁移复盘：当前的单机 SQLite 能支撑什么规模、什么信号出现时才需要消息队列、什么信号出现时才需要对象存储、什么信号出现时才需要更强的隔离。你不会把一次漂亮演示当作可靠结论，也不会把"未来可能扩展"当作立刻上云的理由。

## 你现在站在哪里

阶段 06 已经把执行权变成了可恢复的协议，但系统可能仍然只在本地可用，可能没有明确的成本证据，可能在日志中泄露了原始输入，可能无法回答"一次失败为何发生"。本阶段把"能跑"转成"能被解释、审计和演进"——这是从学生项目到可信交付的最后一步。

## 两份 Skill 在本阶段的角色

`teach-generator` 要求来源、质量和人工审核不是口头承诺，最终证据包要能显示这些决定确实发生过。`humanizer-zh` 的结果应被记录为语言质量证据，但不能被扩大为总体发布保证。Skill 的文本不应无控制地写入用户可见的 Trace——必要的规则摘要应避免泄露内部内容。

## 证据包图

```text
Course / Run
  -> Command
  -> NodeExecution
  -> Event / Trace
  -> Artifact(version)
  -> Finding / Repair / Verification
  -> Budget records
  -> Human decision
  -> delivery evidence packet
```

证据包不是复制全部日志——那会让读者迷失在噪音里。证据包应该让读者能回答四个问题：发生了什么、谁做了决定、失败后系统如何收敛、成本和隐私是否越界。如果你的证据包不能回答这四个问题，它就不是一份合格的交付物。

## 分步任务

### 任务 1：定义 Trace 关联字段

为 Run 定义 trace_id 或等价关联，为 Command、NodeExecution、Artifact、Finding 记录关联键，让前端只显示必要摘要。完成定义是你可以从页面上的一个 Run 标识追到后端的所有相关事实。证据是关联完整性测试——确认从 trace_id 出发能查到所有关联对象。

### 任务 2：记录预算

记录 Provider 调用次数，记录每次调用的成本估算或 token 使用量，记录每轮质量修复的消耗。达到阈值时产生可见事件，超限进入人工决定。完成定义是预算不是事后猜测——你在 Run 执行过程中就能看到消耗。证据是超限夹具，确认达到阈值后系统触发了预期的行动。

### 任务 3：建立脱敏边界

列出 Intake 中的敏感字段，定义日志中允许出现的字段，定义 Artifact 是否可以存原文，对 Trace 中的敏感信息做脱敏或哈希。禁止把密钥写入证据。完成定义是测试能发现泄露——如果你不小心把原始输入写进了日志，脱敏测试应该失败。证据是脱敏测试。

### 任务 4：编写三路径证据

正常路径使用 Fake Provider，从课程需求到人工 release。恢复路径模拟 Worker 崩溃或重复领取，确认接管行为正确。人工路径提交 STOP、REVISE 或拒绝 release，确认人工控制有效。每条路径保存标识、响应、截图和测试结果。完成定义是第三人可以复现你的判断——他不需要你的解释，只需要看证据包就能得出相同的结论。证据是阶段证据记录。

### 任务 5：完成迁移复盘

记录当前规模假设——单机、SQLite、本地 Worker。记录当前单机 SQLite 的限制——并发、数据量、可用性。记录何种信号才需要队列——当并发 Run 超过单 Worker 处理能力时。记录何种信号才需要对象存储——当 Artifact 体积超过本地文件系统合理范围时。记录何种信号才需要更强隔离——当多个租户或安全边界出现时。完成定义是不把"先进架构"当默认答案——你引入新组件是因为观察到了风险，而不是因为大家都在用。证据是风险到机制的矩阵。

### 任务 6：生成交付结论

结论必须区分已验证与未验证——"正常路径已验证，恢复路径已验证，10 个并发 Run 未验证"。结论必须列出已知限制——"单机 SQLite，最大 Artifact 大小未测试"。结论必须列出发布权归属——"release 决定由人做出，系统不自动发布"。结论必须列出后续迁移门槛——"当并发 Run 超过 5 时考虑引入队列"。完成定义是不掩盖失败和未验证项。证据是完整证据包索引。一份诚实的交付结论，比一百次成功演示更有说服力。

## 关于交付证据的补充说明

这是最后一个阶段，也是最容易被"草草了事"的阶段。你可能会想："系统已经能跑了，证据包不就是把测试结果贴一贴吗？"如果这样想，你就会错过本阶段最重要的学习目标：学会区分"系统能跑"和"系统可信"。

**证据包不是测试报告。** 测试报告告诉你"哪些测试通过了"，证据包告诉你"在什么条件下、谁做了什么决定、系统如何响应、结果是什么"。它们是不同层次的信息。例如，测试报告说"Worker 崩溃恢复测试通过"，证据包说"在 Run #42 的 generation 节点执行期间，Worker A 在写入 checkpoint 后崩溃，lease 在 30 秒后过期，Worker B 接管，从 checkpoint 恢复，确认 Artifact 未重复写入，generation 节点重新执行成功"。前者是摘要，后者是叙事。第三人可以通过叙事独立判断系统是否可信，但不能仅凭摘要做出判断。

**迁移判断的诚实性。** 迁移判断最容易犯的错误是"因为大家都在用，所以我们也应该用"。队列、对象存储、Kubernetes——这些技术本身没有问题，但如果你不能说出"当前系统的哪个具体瓶颈需要它们来解决"，你就是在为想象中的问题引入真实的复杂性。一个诚实的迁移判断应该包含三个要素：观察到的具体风险（"当前单 Worker 在处理 5 个并发 Run 时出现了明显的排队延迟"）、提议的机制（"消息队列可以将 Command 的受理和执行解耦"）、引入后的新风险（"消息队列引入了消息丢失和重复投递的可能，需要额外的确认和去重机制"）。

**脱敏不是事后补救。** 如果你在写代码的时候就把原始输入直接写进日志，然后在本阶段用正则表达式去"清洗"日志，那你的脱敏策略已经失败了。脱敏应该在数据进入日志或 Trace 之前就完成——在日志记录函数内部做脱敏，而不是在日志输出之后。你需要定义清楚哪些字段是敏感的（Intake 中的用户输入、可能的密钥字段、Skill 中的内部规则），然后在写日志的代码中显式地跳过或哈希这些字段。这才是"设计安全"而不是"事后补救"。

### 关于测试策略的说明

本阶段的测试验证的不是"功能是否正常"，而是"证据是否可信"。第一组：关联完整性测试——从 trace_id 出发，确认能查到对应的 Command、NodeExecution、Artifact、Finding 和人工决定。第二组：脱敏测试——在日志和 Trace 中搜索敏感字段，确认它们已被脱敏或哈希。第三组：预算超限测试——确认预算达到阈值后触发了事件和人工通知，而不是静默继续。第四组：三路径证据测试——正常路径、恢复路径和人工路径各运行一次，确认每条路径的证据都可以独立复查。这些测试的意义不在于"通过"，而在于"让第三人可以独立验证"——如果测试本身不能说明问题，那证据包就是不可信的。

## AI 交付后的人类 Review
AI 交付代码之后，你打开证据包，假装自己是一个没有参与过这个项目的第三方审查者。你能从证据包中独立判断出"这个系统在正常、恢复和人工干预三种情况下分别表现如何"吗？你能找到预算消耗的记录吗？你能确认敏感数据没有被泄露吗？如果你需要作者的解释才能理解证据包，那证据包还不够完整。


检查每条证据是否能关联到具体的 Run——不能是"某次运行"，必须是"Run #42"。检查恢复路径是否真的发生过失败——不是模拟的，是实际触发过崩溃然后接管。检查人工路径是否有真实的人类决定——是谁、在什么时候、做了什么决定。检查预算是否有阈值后的行动——不是只显示一个数字，而是超限后有明确的事件或人工通知。检查日志和页面是否脱敏——原始输入不应该出现在任何地方。检查 Humanizer 的结果没有被扩大解释——它只是语言质量，不是课程正确性的保证。检查已验证和未验证是否被分开列出。检查迁移建议是否由风险驱动——不是因为"大家都在用 Kafka"，而是因为"当前单 Worker 已经无法在合理时间内处理并发 Run"。检查技术方案是否列出了生产限制。


### 遇到验收问题时

如果你在验收时发现 Trace 关联断裂、预算超限无行动、敏感数据出现在日志中、迁移建议缺少风险依据——先自行检查 Trace 关联、节点和产物记录、质量与审批事实、预算记录、脱敏输出和交付索引。然后让 AI 判断问题是关联模型、事件遗漏、预算计算、阈值行动、脱敏策略、读模型、证据完整性还是迁移判断。确认根因后给最小修复和回归测试。

## AI 做完后重点关注什么

抽查证据包能否从一个 Run 标识反查到执行记录、内容产物、质量 Finding 和人工决定——如果中间有断层，说明 Trace 关联不完整。检查预算和脱敏是可测试的行为，而不只是文档里的承诺。把迁移建议严格限定在已观察到的风险上——如果你还没有遇到并发瓶颈，就不要建议引入消息队列。

在节点副作用后模拟 Worker 崩溃，让 lease 过期并由新 Worker 接管。确认没有重复 Artifact，确认 Trace 说明了接管原因，确认预算记录没有重复计算。保存命令、checkpoint、节点和事件证据。

### 人工路径

让质量预算耗尽或人为提交 REVISE，确认系统等待人而不是自动继续。由人提交停止或修订决定，确认决定可以刷新读取，确认 release 没有自动发生。保存审批和页面证据。

### 解释关

为什么三条路径比一次成功演示更可信？为什么 Trace 不应保存所有原始文本？预算超限后为什么应该有行动而不只是显示一个数字？什么时候才有理由从单机 SQLite 迁移到更复杂的运行时？

## 常见跑偏方式

只贴一张成功截图当证据，把日志当作无需结构的事实，只记录 token 数但不定义超限后该做什么，为方便调试记录密钥和完整敏感输入，把 Humanizer 通过写成"课程正确"，把"未来可能扩展"写成必须立刻上云，将未运行的测试写为已验证。这些做法会破坏交付的可信度——你花了七个阶段建立起来的系统，在最后一步因为证据不可靠而失去说服力。

这些跑偏方式背后有一个共同的根源：把"交付"当成"项目结束"。交付不是项目的终点，它是项目进入下一个阶段的起点。一份好的交付证据包不是在说"你看我做得多好"，而是在说"这是我已经验证的、这是我还没有验证的、这是我在当前规模下的假设、这是我在更大规模下会遇到的挑战"。诚实比完美更有价值——因为诚实让你知道下一步该做什么，而完美让你以为不需要再做什么了。

## 完成后的系统快照

你拥有从两份 Skill 出发的七步 Agent。你拥有可查询的事实与 Artifact。你拥有受控角色、Graph 与质量闭环。你拥有可恢复执行与人工控制。你拥有正常、恢复和人工三条路径的证据。你也明确知道当前实现的限制——单机、本地、未验证并发。这正是一个可以继续演进的项目，而不是一次演示。

每个阶段都是在前一个阶段的基础上建立起来的。你现在做出来的东西，会成为下一阶段的起点——好的起点让你事半功倍，模糊的起点让你举步维艰。花几分钟确认你真的理解了本阶段的每一个设计决策，然后带着信心进入下一阶段。
